架构方案选择

基于 Next.js + PostgreSQL + pgvector + DeepSeek/GLM-4V，三种不同的后端组织方式

A

纯 Next.js 单体（最简）

API Routes 直接调 AI，同步处理

Browser → Next.js API Routes
  ├── /api/assignments → 同步调 GLM-4V
  ├── /api/grading → 同步调 DeepSeek
  └── /api/questions → 同步调 DeepSeek
PostgreSQL + pgvector

优点

  • 最快能跑起来
  • 零额外组件
  • 部署最简单

缺点

  • GLM-4V 图像识别 30s+ 超时
  • 批量作业会阻塞
  • 无法重试失败任务

⚠️ OCR/视觉任务超时是主要风险

B

Next.js + BullMQ 异步队列 ⭐ 推荐

轻量级任务队列处理长耗时 AI 任务

Browser → Next.js API Routes（响应快）
  ├── 创建任务 → Redis Queue
  ├── 查询状态 → PostgreSQL
  └── 获取结果 → PostgreSQL
Worker Process（独立进程）
  ├── 拉取任务 → 调 GLM-4V
  ├── 拉取任务 → 调 DeepSeek
  └── 写结果 → PostgreSQL
Redis（任务队列） + PostgreSQL + pgvector

优点

  • 完全解决超时问题
  • 任务可重试/取消
  • 与产品说明书异步设计吻合
  • Worker 可独立扩容

缺点

  • 需要 Redis
  • 多进程部署
  • 开发稍复杂

✅ 最符合产品说明书设计，生产可用

C

Next.js + 独立 Python AI 服务

前端 Next.js，AI 能力单独一个 FastAPI 服务

Browser → Next.js（UI + 业务 API）
  └── 调用 → FastAPI AI Service
            ├── /ocr → GLM-4V
            ├── /grade → DeepSeek
            └── /generate → DeepSeek
PostgreSQL + pgvector（共享）

优点

  • Python AI 生态更丰富
  • AI 服务可独立升级
  • 未来接 PaddleOCR 更容易

缺点

  • 两套语言维护成本
  • 服务间网络延迟
  • MVP 阶段过度设计

⚠️ MVP 阶段复杂度偏高

技术栈汇总（方案 B）

Frontend: Next.js 15 + TypeScript + Ant Design 5
Backend: Next.js API Routes + BullMQ Workers
Database: PostgreSQL 16 + pgvector
Cache/Queue: Redis 7
AI Text: DeepSeek API（可切换）
AI Vision: GLM-4V API（可切换）
File Storage: 本地 / MinIO / OSS（可配置）
ORM: Prisma
