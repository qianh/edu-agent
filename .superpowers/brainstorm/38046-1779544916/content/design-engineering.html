设计方案 §5：错误处理 · 测试策略 · 工程规范

AI 任务重试 · 三层测试 · 环境变量 · 开发启动

错误处理策略
AI API 调用失败
BullMQ 自动重试策略：
• 重试 3 次，指数退避（5s / 30s / 2min）
• GLM-5V 超时限制：60s per 请求
• 3 次全失败 → job.status = "failed"
• SSE 推送失败通知，前端展示重试按钮
• 写 AIJob.error 字段供审计查看
低置信度处理
识别结果置信度 < 70%：
• 不阻断流程，标记为 needs_review
• 前端用橙/红色视觉提示教师
• 「全部确认」按钮变灰，需逐一处理低置信项
• 低置信结果不触发 MasteryUpdateWorker
文件处理失败
上传大文件超出限制 → 前端校验拦截（<20MB）
图片格式不支持 → 上传前检查 MIME 类型
MinIO 上传失败 → 事务回滚，不创建 submission 记录
GLM-5V 图像无法解析 → 返回 parse_error，提示重新拍摄
API 错误响应规范
// 统一错误格式
{ error: { code, message, details? } }

// 错误码约定
400 VALIDATION_ERROR
401 UNAUTHORIZED
403 FORBIDDEN      ← 教师越权访问
404 NOT_FOUND
409 CONFLICT       ← 重复提交
422 AI_PARSE_ERROR  ← 图像无法识别
503 AI_UNAVAILABLE  ← 模型 API 不可用
测试策略
① 单元测试（Vitest）
重点测试纯计算逻辑，不 mock AI：
• mastery/calculator.ts：掌握度更新算法
  多种场景：首次/重复错/权重/趋势
• ai/provider.ts：模型路由选择逻辑
• lib/confidence.ts：置信度分档规则
• 错因标签映射与知识点匹配规则
② 集成测试（Vitest + 测试 DB）
测试 API Routes + Prisma（用测试数据库）：
• 作业上传流程：创建记录→入队→状态查询
• 教师确认：分数更新→画像触发→报告生成
• 权限隔离：教师只能访问自己班级数据
AI Worker 用 mock provider 替代真实 API
③ E2E 测试（Playwright）
覆盖 3 条核心主流程：
• 上传未批阅作业 → AI 批改 → 教师确认 → 画像更新
• 上传已批阅作业 → 识别结果 → 确认入库
• 学生详情 → 生成试题 → 审核保存
AI 输出质量验收
独立验收脚本（非 CI）：
• 准备 20 份标注好的作业样本
• 对比 GLM-5V 识别结果 vs 人工标注
• 目标：批阅痕迹识别准确率 ≥ 85%
• 目标：扣分识别准确率 ≥ 90%
• 不满足则调整 prompt，不改架构

开发启动 & 部署
# 依赖
pnpm install

# 基础设施（Docker）
docker compose up -d
# → PostgreSQL + Redis + MinIO

# 数据库初始化
pnpm prisma migrate dev
pnpm prisma db seed

# 启动（开发）
pnpm dev          # Next.js :3000
pnpm worker      # BullMQ Worker

# 生产部署
docker compose -f compose.prod.yml up
# → next start + worker + pg + redis + minio
docker-compose.yml 服务：
web（Next.js）· worker（BullMQ）
postgres · redis · minio
共 5 个容器，单机可运行
