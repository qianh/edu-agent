架构方案选择（更新：GLM-5V）

基于 Next.js + PostgreSQL + pgvector + DeepSeek / GLM-5V，重新评估三种方案

🔄 GLM-5V 重新评估
GLM-5V 相比 4V：推理速度更快、图像理解更强、手写/印刷混排识别更准。
但对架构选型的核心影响是：单张图处理时间压缩（约 8–15s），批量仍需异步。
A

纯 Next.js 单体

API Routes 直接调 AI，同步处理

Browser → Next.js API Routes
  ├── /api/assignments → GLM-5V（单张 ~10s）
  ├── /api/grading → DeepSeek
  └── /api/questions → DeepSeek
PostgreSQL + pgvector
GLM-5V 重评：单张处理约 8–15s，Vercel/标准 Node 默认超时 30s，单张勉强可行，但一次上传多页/多学生仍会超时。MVP 阶段单学生单页上传可 workaround，但不稳健。

优点

  • 零额外组件
  • 最快能跑起来
  • GLM-5V 速度提升后单张可用

缺点

  • 多页/多学生仍超时
  • 无重试机制
  • 教师等待 UI 体验差
B

Next.js + BullMQ 异步队列 ⭐ 推荐

API 秒级响应，Worker 后台处理 AI 任务

Browser → API Routes（立刻返回 task_id）
  └── 入队 → Redis/BullMQ
Worker Process
  ├── 图像预处理 → GLM-5V（每张 ~10s）
  ├── 文本分析 → DeepSeek
  └── 写结果 → PostgreSQL
前端轮询/SSE → 实时进度
PostgreSQL + pgvector + Redis
GLM-5V 重评：速度提升让 Worker 吞吐量更高，单 Worker 每分钟可处理 4–6 张。班级 40 人作业约 10 分钟完成，完全符合产品说明书"异步通知"设计。

优点

  • 彻底解决超时
  • 可重试/取消/进度
  • GLM-5V 速度↑ Worker 吞吐更好
  • 符合产品异步设计

缺点

  • 需要 Redis（Docker 一行搞定）
  • Worker 需单独进程

✅ 推荐：GLM-5V 速度提升让这个方案效果更好，而不是让 A 方案够用

C

Next.js + Python FastAPI AI 服务

AI 能力单独服务，前后端分离语言

Next.js → FastAPI AI Service
  ├── /ocr → GLM-5V
  ├── /grade → DeepSeek
  └── /detect-marks → GLM-5V
PostgreSQL + pgvector（共享）
GLM-5V 重评：影响不大。Python 调 GLM-5V 的 SDK 体验与 JS SDK 相近，不构成语言切换的新理由。MVP 阶段两套语言维护成本依然偏高。

优点

  • AI 服务可独立扩容
  • 后续接本地模型/PaddleOCR 更易

缺点

  • 两套语言维护
  • MVP 过度设计
  • 服务间网络跳
更新后技术栈（方案 B）

Frontend: Next.js 15 + TypeScript + Ant Design 5
Backend: Next.js API Routes + BullMQ Workers
Database: PostgreSQL 16 + pgvector
Cache/Queue: Redis 7
AI 文本/推理: DeepSeek API（可切换）
AI 视觉识别: GLM-5V API（批改痕迹识别、作业图像理解）
ORM: Prisma
文件存储: MinIO（本地）/ 阿里云 OSS（云端）可配置
